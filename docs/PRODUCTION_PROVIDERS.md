# اتصال سرویس‌های Production

Adapterهای انتخاب‌شده: زرین‌پال v4 برای پرداخت، کاوه‌نگار برای SMS/OTP، SMTP با TLS
برای ایمیل، ClamAV برای اسکن و S3-compatible برای نگهداری فایل. محیط محلی همچنان mock و
Storage محلی دارد. فایل `.env.production.example` قرارداد تنظیمات است؛ تمام مقدارهای
نمونه باید جایگزین و `LIVE_PROVIDERS_ENABLED=true` صریحاً ثبت شود. صرف واردکردن کلیدها
مجوز فعال‌سازی نیست و فایل تنظیمات خصوصی نباید وارد Git شود.

## پرداخت

مبلغ داخلی تومان است و Adapter آن را دقیقاً ده برابر به ریال تبدیل می‌کند. درخواست سمت
سرور ساخته می‌شود؛ Web فقط برای پاسخ غیر mock به دامنه ثابت زرین‌پال می‌رود. بازگشت به
صفحه سفارش دارای paymentId است و مشتری «بررسی نتیجه پرداخت بانکی» را می‌زند. پارامترهای
بانک مانند Status یا Authority مبنای تسویه نیستند: API شناسه و مبلغ ثبت‌شده در DB را با
درگاه verify می‌کند. فقط code عددی 100 یا 101 موفق است. عدم پاسخ یا پرداخت ناتمام قابل
بررسی مجدد می‌ماند و Worker نیز بررسی می‌کند. تغییر Driver در میانه عمر پرداخت باعث
تسویه با Driver اشتباه نمی‌شود؛ پشتیبانی باید پرداخت‌های باز را تعیین تکلیف کند.

## پیامک و ایمیل

OTP از الگوی تأییدشده `KAVENEGAR_OTP_TEMPLATE` استفاده می‌کند؛ اعلان معمولی از خط خدماتی
`KAVENEGAR_SENDER`. پارامترها در body هستند و متن خطای Provider وارد Log یا پاسخ کاربر
نمی‌شود. SMTP گواهی TLS را اعتبارسنجی می‌کند، دسترسی فایل/URL برای محتوای ایمیل بسته
است و Message-ID از شناسه پایدار اعلان ساخته می‌شود. SMTP و ارسال معمولی پیامک تضمین
exactly-once ندارند؛ قطع ارتباط پس از پذیرش Provider می‌تواند در retry اعلان تکراری
بسازد. Message-ID به پیگیری کمک می‌کند ولی جای deduplication سمت دریافت‌کننده را نمی‌گیرد.

## Storage و اسکن

Bucket باید خصوصی، با TLS و رمزنگاری AES256 سمت سرور باشد. حساب سرویس فقط مجوزهای
GetObject/PutObject/DeleteObject و ListBucket روی prefix اختصاصی `niazat-files/` لازم
دارد؛ مجوز عمومی یا ACL عمومی لازم نیست. نسخه‌بندی Bucket و Retention پشتیبان را در
پنل Storage فعال کنید. محتوای فایل از API و پس از کنترل مالکیت و مجوز یک‌بارمصرف عبور
می‌کند. Quarantine روی Volume خصوصی باقی می‌ماند و فایل پیش از قبولی ClamAV به S3 نمی‌رود.
اسکن مجدد، پاکسازی و Readiness از همان Adapter Storage استفاده می‌کنند.

برای تغییر Storage از local به S3، ابتدا نوشتن فایل متوقف، موجودی DB و checksum فایل‌های
clean استخراج و با همان storageKey به prefix مقصد کپی شود. تعداد، اندازه و SHA256 همه
فایل‌ها را تطبیق دهید و دانلود چند نقش را در staging بیازمایید. سپس Driver تغییر کند.
فایل‌های محلی قبلی را تا پایان پنجره بازگشت حفظ کنید؛ تغییر Driver خودکار فایل‌های قدیمی
را جابه‌جا نمی‌کند. در نصب تازه این مرحله لازم نیست.

## حدود شواهد و پذیرش اتصال زنده

تست‌های خودکار خطا، قالب درخواست، تبدیل مبلغ، جلوگیری از مسیر نامعتبر، TLS و S3 خصوصی
را با پاسخ کنترل‌شده می‌آزمایند. Readiness پرداخت/پیامک/ایمیل صحت تنظیمات را گزارش می‌کند،
نه اعتبار اعتبارنامه یا موجودی حساب Provider. Readiness Storage واقعاً write/read/delete
را اجرا می‌کند. پیش از انتشار عمومی، با حساب‌های تأییدشده در staging این موارد ثبت شوند:

- یک پرداخت موفق، لغوشده و verify تکراری؛ تطبیق مبلغ بانک، payment، ledger و escrow.
- ارسال OTP به شماره مجاز و یک اعلان آزمایشی؛ بررسی خط خدماتی و تحویل Provider.
- ارسال ایمیل به گیرنده مجاز؛ بررسی SPF/DKIM/DMARC و عدم رد شدن توسط SMTP.
- آپلود/دانلود فایل، خطای دسترسی Bucket و قطع اسکنر؛ فایل مشکوک نباید قابل دانلود شود.

این پذیرش زنده هنوز انجام نشده و به کلیدها و حساب‌های مالک پروژه وابسته است.
