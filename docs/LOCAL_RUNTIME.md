# فایل‌های حجیم محیط توسعه

کد و اسناد اصلی پروژه چند مگابایت‌اند. افزایش حجم پروژه پس از نصب و اجرا مربوط به
وابستگی‌ها، خروجی Build و Cacheهای قابل بازسازی است؛ این فایل‌ها جزو کد منبع نیستند.

همه فایل‌های حجیم محلی در پوشه زیر نگهداری می‌شوند:

```text
_runtime/
  apps/
    api/
      node_modules/
      storage/
    web/
      node_modules/
      .next/
```

پوشه `_runtime` در Git ثبت نمی‌شود و هنگام تحویل صرفاً کد می‌توان آن را کنار گذاشت.
مسیرهای استاندارد `apps/*/node_modules`، `apps/web/.next` و `apps/api/storage` فقط Junctionهای سبک به همین
پوشه‌اند تا دستورات معمول `npm` و Next.js همچنان کار کنند.

خروجی کوچک `apps/api/dist` داخل خود شاخه API ساخته و در Git نادیده گرفته می‌شود؛ Nest هنگام هر build این
پوشه را پاک و بازسازی می‌کند، بنابراین Junction کردن آن پایدار نیست. این پوشه کد منبع نیست و برای انتقال سورس
می‌توان آن را کنار گذاشت.

## مدیریت اتصال‌ها

از ریشه پروژه اجرا کنید:

```powershell
# مشاهده وضعیت
powershell -ExecutionPolicy Bypass -File .\scripts\runtime.ps1 status

# نصب تمیز وابستگی‌ها، مستقیماً داخل _runtime
powershell -ExecutionPolicy Bypass -File .\scripts\runtime.ps1 install

# اتصال محیط حجیم برای توسعه
powershell -ExecutionPolicy Bypass -File .\scripts\runtime.ps1 attach

# جداکردن اتصال‌ها پیش از کپی دستیِ صرفاً کد
powershell -ExecutionPolicy Bypass -File .\scripts\runtime.ps1 detach
```

`detach` فقط Junctionهای شناخته‌شده را برمی‌دارد و محتوای `_runtime` را حذف نمی‌کند.
اگر در یکی از مسیرها یک پوشه واقعی وجود داشته باشد، اسکریپت برای جلوگیری از حذف اشتباه
متوقف می‌شود.

دستور `install` فایل‌های کوچک manifest را به محیط محلی کپی می‌کند، `npm ci` را همان‌جا اجرا می‌کند و سپس
Junctionها را متصل می‌کند؛ بنابراین خود پکیج‌ها هیچ‌وقت داخل بخش کد منبع قرار نمی‌گیرند.

## اجرای یکپارچه لوکال

```powershell
# اجرای API و Web در پنجره‌های مخفی و انتظار برای Health
powershell -ExecutionPolicy Bypass -File .\scripts\local.ps1 start

# مشاهده وضعیت فرایند و Health
powershell -ExecutionPolicy Bypass -File .\scripts\local.ps1 status

# توقف امن همان فرایندهایی که اسکریپت اجرا کرده است
powershell -ExecutionPolicy Bypass -File .\scripts\local.ps1 stop
```

PID و Logها فقط در `_runtime/pids` و `_runtime/logs` ذخیره می‌شوند. اسکریپت پیش از توقف، شناسه و زمان
شروع فرایند را تطبیق می‌دهد تا یک PID قدیمی باعث توقف برنامه نامرتبط نشود.

## ورود و ثبت‌نام در محیط توسعه

### ابزار توسعه و خطاهای کنسول

فرمان Web اکنون `next dev --webpack` است؛ build انتشار همان `next build` با Turbopack باقی است. در نسخهٔ نصب‌شدهٔ 16.3.4، مرز ریشهٔ ۴۰۴ به‌علت واردسازی مستقیم منوی عمومی، CSS مشترک را برای مسیرهای سالم preload می‌کرد؛ صفحه CSS بزرگ‌ترِ هم‌پوشان را مصرف می‌کرد و لینک بستهٔ کوچک‌تر فعال نبود. اصلاح اول، مرز کلاینت ۴۰۴ با `next/dynamic` برای منوی کامل و SSR فعال است؛ منو و CSS هنگام نیاز بارگذاری می‌شوند. تغییر ابزار به‌تنهایی نیز کافی نبود و هشدار `app/not-found.css` در Webpack تکرار می‌شد.

پس از اصلاح ۴۰۴، بارگذاری تازه در Turbopack بدون هشدار بود، اما آزمون واقعی تغییر و برگشت CSS هنوز دو خطای `No link element found for chunk` داد. بنابراین اصلاح دوم استفاده از Webpack فقط در توسعه است. ترکیب دو اصلاح در آزمون ویرایش و برگشت استایل موفق شد: بدون reload، حفظ وضعیت صفحه، یک اتصال و بدون خطای CSS. این راهکار سازگاری نسخهٔ نصب‌شده است؛ patch کتابخانه، مخفی‌سازی هشدار، تغییر build یا وابستگی جدید ندارد. کامپایل اولیهٔ توسعه ممکن است کندتر باشد.

پس از راه‌اندازی مجدد سرور، تب قدیمی را با `Ctrl+Shift+R` تازه کنید؛ runtime قبلی نباید با chunkهای جدید مخلوط شود. پیام پیشنهاد React DevTools و یک `[HMR] connected` عادی‌اند؛ تکرار بی‌وقفه یا خطای CSS عادی نیست. کنسول فیلتر یا خاموش نشده است.

با سرور روشن، `npm --prefix apps/web run dev:smoke` چهار صفحه را در context مهمان مستقل بررسی می‌کند: ۵ ثانیه راه‌اندازی با حداکثر یک reload کامپایل سرد، سپس ۱۲ ثانیه بدون هیچ اتصال مجدد، دقیقاً یک socket فعال، بدون خطای JavaScript و بدون هشدار CSS استفاده‌نشده. Next در تغییر hash کامپایل سرد یک full reload انجام می‌دهد؛ این با حلقهٔ اتصال مجدد متفاوت است و نباید کل مشاهده را به شمار کل handshakeها تقلیل داد. برای Chrome نصب‌شده، متغیر `PLAYWRIGHT_EXECUTABLE_PATH` را روی مسیر فایل اجرایی آن قرار دهید. تست از نشست واقعی کاربر استفاده نمی‌کند و دیتابیس را تغییر نمی‌دهد.

۴۰۱ اولیهٔ `/auth/me` ممکن است پیش از تمدید خودکار رخ دهد؛ موفقیت `/auth/refresh` و درخواست بعدی ملاک است. برای مهمان، ۴۰۱ refresh نیز قابل انتظار است. شکست مداوم درخواست‌های محافظت‌شده بعد از ورود نیاز به بررسی جداگانه دارد و نباید با غیرفعال‌کردن guard پنهان شود.

- زیرساخت احراز هویت واقعی است و همان سیاست امنیتی Production را اجرا می‌کند؛ رمز عبور باید حداقل
  ۱۰ کاراکتر و شامل حرف بزرگ، حرف کوچک، عدد و نماد باشد.
- وقتی `SMS_DRIVER=mock` است پیامک واقعی ارسال نمی‌شود. کد یک‌بارمصرف توسعه در همان صفحه نمایش داده
  می‌شود تا ثبت‌نام و ورود با OTP روی لوکال قابل آزمایش باشد.
- صفحه `/login` هم ورود با رمز و هم ورود با OTP را دارد. در محیط Development دکمه‌های نقش‌های نمایشی
  نیز نمایش داده می‌شوند و فقط فرم را پر می‌کنند؛ ورود همچنان با اقدام صریح کاربر انجام می‌شود.
- مقدار `DEV_DEMO_PASSWORD` فقط در فایل محلی `apps/web/.env.local` نگهداری و از Route سمت سرور خوانده
  می‌شود. این Route در Production پاسخ `204` می‌دهد و هیچ رمز نمایشی داخل Client bundle قرار نمی‌گیرد.
- برای فعال‌کردن حساب‌های نمایشی، `DEV_DEMO_PASSWORD` را مطابق رمز کاربران Seed در فایل محلی تنظیم کنید.
  نمونه متغیر در `apps/web/.env.local.example` وجود دارد و فایل واقعی `.env.local` وارد Git نمی‌شود.

## تست قرارداد فایل امن

پس از اجرای API و Web، این تست یک فایل متنی امن را با حساب نمایشی مشتری آپلود می‌کند، عبور از اسکن،
دانلود با Signed URL یک‌بارمصرف، جلوگیری از استفاده مجدد لینک و رد MIME غیرمجاز را بررسی می‌کند:

```powershell
cd apps/api
npm run phase4:file-contract
```

فایل تست به آخرین سفارش مشتری نمونه متصل می‌شود تا نتیجه در تب «فایل‌ها» نیز قابل مشاهده باشد.

## تشخیص کد واقعی

فهرست قطعی فایل‌های پروژه همان خروجی Git است:

```powershell
git ls-files
```

برای انتقال صرفاً سورس، بعد از `detach` همه فایل‌ها به‌جز `_runtime` و `.git` قابل کپی‌اند.
فایل‌های `package.json` و `package-lock.json` باید همراه سورس بمانند؛ خود پکیج‌ها بعداً با
`npm ci` قابل بازسازی هستند.
