# قرارداد اجرایی Z1 — سفارش و ثبت‌نام

شاهد بسته: ZEUS-EXEC-009، ۲۰۲۶-۱۰-۲۵. این قرارداد، همهٔ ۲۹ API سند D1 یا ۵۵ API سند D3 را پذیرفته اعلام نمی‌کند. مرجع فعلی Next/Nest/Prisma و APIهای پروژه طبق DEC01/09 محفوظ‌اند؛ اتصال زنده تعویقی است.

## نگاشت وضعیت D1 بدون حذف مراحل D4

نه وضعیت سفارش در SQL سند D1، سطرهای ۱۷۸–۱۸۱، هم‌نام و هم‌معنا در enum فعلی حفظ‌اند:

| D1 | وضعیت جاری | فرمان مسئول |
| --- | --- | --- |
| pending_triage | pending_triage | submit، پس از submitted و ثبت صف خودکار |
| triaging | triaging | شروع تریاژ مدیر مجاز |
| assigned | assigned | تخصیص معتبر Ops، پس از پرداخت |
| in_progress | in_progress | پذیرش مجری دارای تخصیص؛ یا بازگشت مجاز اصلاح/اختلاف |
| delivered | delivered | عبور از QC و آماده‌سازی تحویل |
| confirmed | confirmed | تأیید مالک یا worker واجد مهلت؛ نه تأیید به نام مشتری |
| closed | closed | تسویهٔ تراکنشی پس از تأیید، یا حل اختلاف مجاز |
| cancelled | cancelled | فقط یال صریح و قرارداد DEC12 |
| disputed | disputed | ایجاد اختلاف مجاز؛ خروج فقط resolve-dispute |

یازده وضعیت افزوده حذف یا در API به یکی از این نه وضعیت تبدیل نمی‌شوند: draft، submitted، pending_quote، quoted، pending_payment، paid، submitted_for_qc، qc_in_review، qc_rejected، ready_for_customer_review و revision_requested. آن‌ها پیش‌نویس/قیمت/پرداخت/QC/اصلاح را دقیق نگه می‌دارند. «completed» وضعیت پرداخت D1 است، نه مجوز تبدیل مستقیم سفارش به closed. alias عمومی PUT status ساخته نشده است.

## مرز مشترک گذار و اثر مالی

- تمام نوشتن‌های status موجود در کد runtime از OrderWorkflowService عبور می‌کنند. ساخت draft، ویرایش فیلدهای draft، snapshot فرم و اتصال سازمان، گذار status نیستند و CAS/مالکیت خود را حفظ کرده‌اند.
- جدول ۲۰×۲۰ در آزمون مستقل بررسی می‌شود؛ هر گذار CAS وضعیت/version، history و Audit همان تراکنش دارد. شناسه، مالک، version و روابط تو‌در‌توی مالی/history از extraData قابل بازنویسی نیستند. مشتری باید مالک و مجری باید دارای تخصیص فعال باشد؛ Scope مدیر در فرمان/کنترلر مربوط اعمال می‌شود.
- paid فقط پس از تطبیق Payment موفق، مالک/مبلغ/ارز، Ledger واقعی، rail وجه و Escrow متناظر و پوشش کامل قیمت/همه مراحل ثبت می‌شود. wallet و gateway از همان مرز استفاده می‌کنند؛ پارامتر نمایشی یا پرچم paid جای سند مالی نیست.
- تأیید خودکار داخل تراکنش، deliveredAt، مهلت پیکربندی‌شده و نبود اختلاف باز را دوباره کنترل می‌کند. actor آن system/null است؛ Audit، Ledger و history به نام مشتری جعل نمی‌شوند. رقابت تأیید دستی/خودکار فقط یک تسویه دارد.
- تأیید سفارش تمام holdهای تسویه‌نشدهٔ مراحل را آزاد می‌کند. لغو/حل اختلاف با refund_full یا refund_partial، مبلغ مصوب را بین holdها به‌ترتیب قطعی توزیع می‌کند؛ تغییر نرخ بازپرداخت یا آزادسازی خودکار مانده انجام نشده است.
- آزادسازی پیش از تأیید ممنوع است. باقی‌ماندهٔ cancelled/closed فقط با فرمان صریح Finance/Super قابل تعیین تکلیف است. آزادسازی در disputed فقط از فرمان حل اختلاف و scope مجاز، نه DTO مالی عمومی، مجاز است.
- replay در پنجرهٔ Idempotency پاسخ قبلی را می‌دهد؛ پس از انقضای cache، برخورد کلید پایدار Ledger در release/refund با 409 رد می‌شود، نه تکرار تغییر موجودی یا امانی. بازپرداخت/آزادسازی عمومی Finance همچنان قرارداد قبلیِ یک hold را دارد؛ عملیات «کل سفارش» از helper چندhold استفاده می‌کنند.
- لغو و حل اختلاف علت trim‌شدهٔ غیرخالی را واقعاً در اسناد/عملیات مصرف می‌کنند. QC/تحویل/اختلاف میان‌بُر لغو عمومی ندارند. داده/شناسه/اسناد قدیمی بازنویسی نمی‌شوند.

## ثبت‌نام و سازگاری احراز هویت

`POST /v1/auth/register` همچنان phone/fullName/password اختیاری می‌پذیرد؛ پاسخ افزایشی registrationAttemptId دارد. رمز اختیاری بودن، ورود با رمز، OTP ورود، بازیابی، JWT/refresh cookie و چهار نقش حفظ‌اند.

`POST /v1/auth/otp/verify` برای purpose=register علاوه بر phone/code، registrationAttemptId و همان fullName/password درخواست اولیه را می‌خواهد. challenge با hash ثابتِ SHA-256 و سپس bcrypt به همهٔ این فیلدها بسته شده است؛ نام Unicode طولانی محدودیت ۷۲بایتی bcrypt را دور نمی‌زند. اطلاعات/رمز فقط بعد از اثبات مالکیت و CAS فعال‌سازی مصرف می‌شوند. ثبت‌نام مجدد ناشناس، رکورد موجود pending را تغییر نمی‌دهد؛ حساب فعال/غیرمشتری قابل ثبت مجدد نیست.

فرستادن مجدد OTP با purpose=register باید اطلاعات همان فرم را داشته باشد یا از register دوباره استفاده کند؛ درخواست قدیمی phone-only با 400 رد می‌شود و داده/رمز از حدس یا cache ساخته نمی‌شود. OTP ثبت‌نام‌های پیش از این اصلاح، قابل تبدیل به proof جدید نیستند؛ کاربر در همان صفحه اطلاعات را بازبینی و یک کد تازه دریافت می‌کند. مسیر login/password_reset چنین فیلد تازه‌ای لازم ندارد.

- proof اشتباه با 400 و افزایش متعهدشدهٔ attempts پاسخ می‌گیرد؛ سقف پنج، انقضا و مصرف یک‌باره داخل تراکنش‌اند. رقابت فعال‌سازی فقط یک برنده/Audit دارد؛ تعارض serialization با 409 پاسخ داده می‌شود.
- ساخت کیف پول صفر و Ledger account داخل تراکنش فعال‌سازی است؛ حساب Ledger مفقود با موجودی غیرصفر، با حدس موجودی بازسازی نمی‌شود. ثبت‌نام هیچ نقش مجری یا ادغام خودکار حساب اعطا نمی‌کند.
- user_login_states.lastSuccessfulLoginAt هم‌زمان با صدور session ثبت می‌شود؛ سوابق نامعلوم قبلی backfill حدسی ندارند. refresh، ورود تازه محسوب نمی‌شود.
- devOtp فقط development + SMS mock است؛ test/production آن را نمی‌فرستند. ارسال زنده همچنان تعویقی است. رمز و challenge در localStorage/sessionStorage ذخیره نمی‌شوند.
- UI در همان دو تم/اجزای مشترک است. نبود challenge پاسخ، fail-closed است. اصلاح اطلاعات خودکار درخواست تازه نمی‌فرستد؛ کاربر صریحاً «ادامه» می‌زند. خطای کد، فرم را حفظ می‌کند.

## حدود پذیرش

۴۳ مجموعه/۳۱۶ تست API و یک skip قدیمی؛ ۲۶ گروه آزمون ایزوله PostgreSQL/HTTP با JWT و session واقعی؛ ۹ شاخهٔ سفارش و ۴۵ تغییر غیرمجاز ردشده؛ چهار حالت مرورگر ثبت‌نام با API fixture و چهار Axe بدون تخلف. fixture مرورگر اثبات ارسال واقعی SMS نیست؛ fixture تحویل در runner مالی جانشین آزمون کامل QC نیست و شاخه‌های کامل سفارش جدا اجرا شده‌اند. baseline تصویری ۱۹۲گانه تغییر نکرده است.

این بسته migration تازه، تغییر package/lock، تراکنش پذیرش روی DB اصلی، seed/reset، اصلاح موجودی قدیمی، Provider زنده، commit/push یا پذیرش CI ندارد. زئوس Z1.1 (تطبیق کامل داده/snapshot) و Z1.3 (تمام قراردادها/ماتریس HTTP) همچنان بازند؛ ثبت‌نام و lastLogin پیشرفت مشخص همین بندها هستند، نه تکمیل همهٔ آن‌ها.
