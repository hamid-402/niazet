# Z3 — بستهٔ مستقل هویت تأییدشده و اطلاعات درخواست

مجوز صریح مالک: ۲۰۲۶-۱۰-۲۸، پس از بستهٔ پذیرفته/فعال و pushشدهٔ `c166209`. این بسته تکمیل UI-011/012/017 است؛ گواهی continuation تاریخی می‌ماند و به‌معنی پذیرش سورس تازه نیست. تکمیل کل Z3، CI یا اتصال زنده ادعا نمی‌شود.

## وضعیت جاری و ازسرگیری — ۲۰۲۶-۱۰-۲۸

### پایان زیر‌بستهٔ بکند؛ رابط و فعال‌سازی هنوز باز

- گیت مستقل `node scripts/acceptance/zeus-z3-identity-intake-backend-gate.mjs` موفق است. گواهی `docs/zeus/z3-identity-intake-backend-acceptance.json` صریحاً فقط `backendAccepted=true` دارد؛ UI، کل Z3، فعال‌سازی اصلی، CI و Provider زنده پذیرفته نشده‌اند. وضعیت همچنان **۳ فاز کامل از ۱۰ فاز؛ Z3 جاری** است.
- آخرین اجرای کامل API: **۵۵ مجموعه، ۵۴۷ موفق و یک skip قبلی**؛ typecheck، lint و build موفق. پس از اصلاح صرفاً نوع/قالب، کنترل حساس مرتبط و خروجی ساختاریافتهٔ نهایی Jest نیز موفق شد. تمام ۳۵ تست محافظ/تاریخی مرتبط و بررسی diff موفق‌اند. آزمون‌های نامرتبط Web یا ماتریس تصویری در این زیر‌بسته تکرار/به‌روز نشدند.
- پذیرش واقعی `zeus-z3-identity-upgrade.mjs --with-email --with-customer-intake`: چهار گروه migration، ده گروه ایمیل و هشت گروه onboarding/intake/export موفق؛ DB تصادفی و کلاینت‌های موقت همان آزمون پس از کنترل مسیر حذف شدند. داده و ستون‌های هر۷۸جدول قبلی برابرند؛ کلاینت واقعی قبلی روی DB۲۸ و کلاینت جدید روی DB۲۷، هر۷۸مدل را خواندند و write/restore fixture برابر بود. هیچ اتصال به DB اصلی/Provider زنده انجام نشد.
- ایمیل: controller اکنون در **AuthModule واقعی** ثبت و از همان AppModule/guard/ValidationPipe/session آزموده شده است. ده گروه، proof مالکیت، تصادم حساب قدیمی، expiry/replay/resend/failure، عدم افشای token در test/production/Audit، refresh و سه race واقعی تغییر ایمیل، race بازیابی رمز، lockout مشترک و سقف مشترک ده تلاش را پوشش می‌دهند. هیچ حسابی ادغام نشده و ورود phone/OTP/password قبلی حفظ است.
- onboarding: GET حساب قبلی چیزی نمی‌سازد؛ ثبت/skip اختیاری، CAS و retry idempotent و رقابت دو انتخاب متفاوت پذیرفته‌اند. علاقه به همکاری هیچ نقش/قابلیتی نمی‌دهد. UI آینده صرفاً رسیدگی انسانی از پشتیبانی را معرفی می‌کند؛ ثبت درخواست همکاری یا اعطای مجری را وانمود نمی‌کند.
- intake: همهٔ هشت نوع داده رفت‌وبرگشت دارند؛ autosave بدون ارسال دوبارهٔ intake آن را حفظ می‌کند، clear صریح فقط metadata پیش‌نویس را پاک می‌کند و پاسخ اصلی فرم حفظ می‌شود. فیلد هم‌معنا با کلید صریح نگاشت، تناقض رد و دادهٔ معتبر قدیمیِ غیرقابل‌تلخیص بدون تغییر در snapshot اصلی حفظ می‌شود. submit واقعی با همان دو گذار، metadata را در همان تراکنش و با version واقعی seal می‌کند؛ بعد از ثبت حتی UPDATE/DELETE مستقیم نیز در DB ایزوله رد شد.
- اطلاعات کامل فقط برای مالک و endpoint محدود Ops است؛ Finance/Support/مجری به endpoint کامل دسترسی ندارند. مجری فقط پس از کنترل تخصیص قبلی، projection هدف/برند/نمونه/محدودیت را می‌گیرد؛ یادداشت مالی و ترجیحات خصوصی به projection تازه نمی‌روند و پس از لغو تخصیص دسترسی قطع است. این ادعا دربارهٔ projection جدید است، نه بازتعریف خودکار سیاست دسترسیِ فرم‌های قدیمی.
- درخواست محرمانگی بالاتر/تحویل مرحله‌ای/افزودنی حتی با خاموش‌کردن flag رابط، از قیمت قطعی خودکار عبور نمی‌کند؛ rollback سفارش/history/Quote/پول آزموده شد. این ترجیح‌ها مبلغ، ACL یا milestone ایجاد نمی‌کنند. سفارش عادی با اطلاعات معمول، قیمت مصوب قبلی را می‌گیرد.
- خروجی حریم خصوصی قبلی با همهٔ بخش‌های قدیمی حفظ و اطلاعات جدیدِ فقط مالک به آن اضافه شد؛ hash رمز/challenge، proof داخلی و tag نشست صادر نمی‌شوند. snapshot همهٔ جدول‌های مالی آزمون و نقش/قابلیت مشتری‌ها قبل و بعد برابر بود؛ ساخت/حذف پروفایل مجری فقط fixture صریح آزمون projection بود، نه اثر onboarding.
- استثنای مستقل `orbit-z3-identity-intake-approval.mjs` فقط **۲۸ مسیر API و پنج آداپتور دقیق** دارد؛ inverse فقط با هش قبل/بعد معتبر و checkpoint `c166209` عمل می‌کند. baseline همچنان `2c701d7` است؛ تمام فایل‌های API بیرون دامنه و تمام scalar/enumهای قبلی حفظ شدند، متدهای غیرمرتبط auth/حساب/سفارش AST برابر دارند. تغییر یک‌بایتی/فایل گم‌شده/مسیر ناشناس رد می‌شود؛ گواهی‌های قدیمی عیناً محفوظ و قبولی سورس جدید شمرده نشده‌اند.
- یک assertion تاریخی B3 پس از اضافه‌شدن استثنای تازه، به‌درستی schema جدید را رد کرد؛ آداپتور فقط شناسایی pin تازه و بازسازی دقیق checkpoint قبلی را اضافه کرد. مسیر افزودهٔ دقیقِ فاقد نسخهٔ تاریخی با گواهی مستقل جاری آزموده می‌شود؛ نه مقایسه با فایل تاریخی ناموجود یا waiver پوشه‌ای. نقص وابستگی خصوصی `@prisma/internals` در تست تازه با parser آزموده‌شدهٔ موجود پروژه رفع شد؛ نصب جدید/حذف معیار انجام نشد. بازاجرای تجمیعی۳۵تایی بدون شکست موفق بود.
- API `http://localhost:3001/health` و Web `http://localhost:3002` هر دو۲۰۰؛ `/v1/health` endpoint سلامت نیست و۴۰۴ آن خاموشی محسوب نشد. DB اصلی همچنان۲۷، دو flag خاموش و کلاینت اصلی پیش از فعال‌سازی نهایی نیازمند generate هماهنگ است. علت خاموشی قابلیت تازه، **بازبودن رابط/پذیرش کل بسته** است، نه مانع حل‌نشدهٔ تست بکند.

**نقطهٔ ادامهٔ دقیق:** ابتدا Web AGENTS و راهنمای نصب‌شدهٔ Next مربوط به بخش تغییرکرده؛ سپس UI ورود ایمیل/تأیید مالکیت پروفایل، onboarding غیرمسدودکننده، ویرایشگر intake مرحله۲ با حذف سؤال تکراری معنایی، autosave/مرور/جزئیات مالک/Ops/مجری. همان دو تم و primitives، بدون تغییر قرارداد مالی/نقش. مشکل تغییر خدمت پس از ساخت draft نیز باید با مسیر صریحِ حفظ پیش‌نویس و فایل‌ها حل شود؛ تغییر صرفاً client-side خدمت که draft سرور را عوض نمی‌کند پذیرفته نیست. سپس آزمون واقعی مرورگر/دسترس‌پذیری، pin مستقل UI و گیت کل بسته، migration افزایشی/فعال‌سازی امن لوکال با حفظ داده. کارت‌های دیگر Z3 و CI/Providerهای تعویقی جدا باز می‌مانند.

### سابقهٔ مراحل میانی همین زیر‌بسته

توقف صریح قبلی مالک رعایت شد؛ نوشتن یادداشت نهایی آن توقف به‌دلیل پایان سهمیهٔ بررسی ابزار اجرا نشد. با دستور بعدی «ادامه بده» کار از همین WIP ازسر گرفته شد، نه از ابتدا. آخرین commit/push پذیرفته همچنان `c166209` است؛ این بسته هنوز WIP و بدون گیت/فعال‌سازی نهایی است.

- schema پنج جدول افزایشی identity/challenge/family/onboarding/intake و چهار قرارداد pure با spec آماده‌اند. ۵۷ آزمون قرارداد، پس از بازخوانی و سقف۳۲۰۰۰ بایت، دوباره موفق شدند؛ format/validate و lint متمرکز موفق بوده‌اند.
- rehearsal نخست migration، چهار گروه قیود و حفظ همهٔ۷۸جدول قبلی را با برابری داده/ستون و کلاینت واقعی قبلی پذیرفت. سپس دو کلاینت موقت مستقل: candidate روی DB۲۷ و قبلی روی DB۲۸، همهٔ۷۸مدل قدیمی را خواندند و write/restore واقعی fixture برابر بود. DB و پوشهٔ آزمون حذف شدند. این پذیرش migration است، نه پذیرش احراز هویت.
- کلاینت اصلی زیر `_runtime` از schema۲۸ generate شد. قفل DLL با توقف/شروع رسمی همان فرایندهای پروژه رفع شد؛ نه حذف DLL، نه install و نه دستکاری DB اصلی. **DB اصلی هنوز migration۲۷ دارد؛ هیچ migration/seed/reset/پذیرش مالی اصلی اجرا نشده است.** مدل‌های قبلی فقط relation افزایشی دارند، نه scalar جدید؛ سازگاری روی DB قدیمی ایزوله آزموده شده است.
- مسیرهای قدیمی همچنان کار می‌کنند؛ سلامت API و Web پس از ازسرگیری با HTTP۲۰۰ تأیید شد. helper وضعیت PowerShell در اجرای بدون تنظیم execution-policy رد شد؛ برای این مشاهده هیچ policy دور زده یا عوض نشد و فقط HTTP فقط‌خواندنی استفاده شد.
- شاخهٔ مشروط proof ایمیلی به password/session افزوده شد: هویت/نسخه/ایمیل و hash رمز واقعاً بررسی‌شده در تراکنش صدور دوباره کنترل می‌شوند. tag خانواده، لغو را پس از refresh/حذف نشست اولیه حفظ می‌کند. تغییر ایمیل یا رمز، proofهای معلق و خانواده‌های ایمیلی مربوط را با trigger افزایشی لغو می‌کند؛ phone/OTP و role/Ledger دست‌نخورده‌اند. ۵۵ آزمون auth شامل قبلی‌ها و ۱۸ مرز جدید موفق؛ typecheck/lint فایل‌های تازه موفق است.
- در مرحلهٔ میانی `VerifiedEmailService`، DTO و controller آماده ولی هنوز در ماژول ثبت نشده بودند؛ **اکنون ثبت و پذیرش مستقل بالای همین سند مرجع است**. ورود ایمیلی با مسیر password/lockout/صدور نشست فعلی کار می‌کند؛ درخواست تأیید به رمز فعلی و ایمیل صریح مقید است، token فقط hash ذخیره می‌شود، تصادم حساب قدیمی ادغام نمی‌شود، resend/failure/expiry/replay receipt کنترل می‌شوند. development/mock تنها حالت نمایش devToken است؛ production یا driver زنده، درخواست/تأیید mock را نمی‌پذیرد.
- کلید `ZEUS_VERIFIED_EMAIL_ENABLED` فعلاً در لوکال اصلی فعال نشده و پیش‌فرض false است؛ برای سازگاری DB۲۷ هیچ خواندن جدول تازه در نشست قدیمی انجام نمی‌شود. پس از گیت و migration پذیرفته‌شده، قابلیت آماده باید روی همین لوکال فعال شود؛ خاموش‌ماندن بی‌دلیل مجاز نیست.
- پذیرش native جدید در `zeus-z3-identity-upgrade.mjs --with-email`، با Nest/guard/ValidationPipe واقعی و درایور ایمیل mock داخل DB تصادفی اجرا می‌شود؛ گزارش جدا `.artifacts/zeus/z3-email-native/report.json`. در زمان ثبت این بند هنوز نتیجهٔ نهایی آن اعلام نمی‌شود. مرحله بعد رفع هر نقص همین پذیرش، سپس onboarding/intake و UI، پین مستقل و گیت مرتبط است. محافظ/گواهی قدیمی نباید قبولی سورس جدید حساب شود؛ drift کنونی خارج از pinهای نه‌فایلی قبلی عمدیِ WIP تأییدشده است، نه استثنای نهایی.

## مرزهای ثابت

- همان چهار نقش، Scopeها، password/phone/OTP/session/refresh، بازیابی و حساب‌های قبلی حفظ شوند. هیچ ادغام خودکار، migration دادهٔ قدیمی، ساخت مجری از علاقه به همکاری یا تغییر Ledger/موجودی مجاز نیست.
- فقط schema/migration افزایشی؛ ابتدا DB تصادفیِ ایزوله، برابرماندن جدول/ستون/رکورد قبلی و کلاینت قبلی. روی DB اصلی پیش از پذیرش مستقل migration/seed/پذیرش مالی انجام نشود.
- استثنای API/auth/data این بسته مستقل از نه فایل ثبت قطعی است؛ مسیر/hash دقیقِ نهایی، inverse با قبل/بعد معتبر و آزمون منفی مستقل لازم است. baseline `2c701d7` و گواهی‌های قدیمی حفظ شوند. هیچ waiver پوشه‌ای یا شمردن گواهی تاریخی به‌عنوان آزمون سورس جدید مجاز نیست.
- UI همان دو تم/پالت/اجزای فعلی؛ onboarding غیرمسدودکننده، بدون CAPTCHA/Provider/AI تازه. SMTP/SMS/درگاه/ذخیره‌سازی/AV زنده همچنان تعویقی است.

## I1 — ایمیل فقط با اثبات مالکیت

1. ایمیل موجود User، به‌تنهایی هویت ورود نیست. binding مستقلِ یکتا و تأییدشده ایجاد شود؛ هیچ backfill/تأیید ضمنی روی داده قدیمی اجرا نشود. برخورد حروف بزرگ/کوچکِ حساب‌های قدیمی، خطای امن/رسیدگی انسانی است، نه انتخاب اولین حساب یا ادغام.
2. ابتدا مالکِ واردشده ایمیل اختیاری پروفایل خود را ثبت می‌کند؛ challenge به همان آدرس و همان user مقید، تصادفی پرآنتروپی، hashشده، یک‌بارمصرف و دارای مهلت محدود است. درخواست دوباره، تغییر ایمیل، مصرف دوباره، نسخه کهنه و رقابت آزموده شوند. raw token وارد log/Audit نمی‌شود.
3. نمایش token آزمایشی فقط شرط صریح development و driver mock؛ محیط production/test حق دریافت token در پاسخ عادی ندارد. mock موفق، ارسال واقعی محسوب نمی‌شود. failure ارسال هیچ binding تأییدشده نسازد.
4. مسیر جدید ایمیل از اثبات binding به همان منطق password/حساب/نشست فعلی متصل شود؛ lockout/rate-limit با شناسه دوم دور زده نشود. خطای ایمیل ناشناس/تأییدنشده/رمز غلط عمومی باشد. race تغییر/لغو ایمیل با login fail-closed؛ هویتِ قدیمی یا تأییدنشده مجوز ورود نگیرد.
5. تغییر/پاک‌کردن ایمیل پروفایل، binding و challenge قدیمی را اتمیک لغو کند. export/deletion/حریم فعلی محفوظ و بدون افشای hash/token باشند. OTP ایمیلی یا بازیابی از ایمیل، از وجود این قابلیت استنباط نشود؛ OTP موبایل و بازیابی قبلی حفظ‌اند.

## I2 — onboarding سبک و اختیاری

- وضعیت نسخه‌دارِ هدف استفاده/skip فقط برای مالک ذخیره شود؛ برگشت/refresh و حساب قدیمی امن باشند. ادامه سایت به completion وابسته نشود. skip و ثبت دوباره رفتار روشن و idempotent داشته باشند.
- «علاقه به همکاری» فقط مقصد جذب فعلی را معرفی کند؛ نه User.role، نه capability یا وضعیت پرسنل را تغییر دهد. ثبت‌نام/تأیید موبایل و صدور نشست فعلی حذف یا بازنویسی غیرضروری نشوند.

## I3 — intake نسخه‌دار و سازگار با draft قدیمی

- هدف، برند/رنگ، نمونه، محدودیت، درخواست سطح محرمانگی، ترجیح تحویل مرحله‌ای، توضیح مالی و درخواست افزودنی، typed و bounded باشند. URL نمونه فقط داده است؛ سرور آن را fetch نمی‌کند. متن آزاد هرگز مبلغ/امانی/milestone/دسترسی تازه نسازد.
- فیلد پویای هم‌معنا با کلید معنایی صریح نگاشت شود، نه تشخیص از label و ساخت دوباره همان سؤال. ورودی متناقض رد شود. snapshot فرم قبلی و پاسخ‌ها عیناً محفوظ؛ سفارش قدیمی بی‌مدرک بازتفسیر/backfill نشود.
- autosave/CAS، رفت‌وبرگشت سه مرحله، reload و update package/service داده را بدون قصد کاربر پاک نکنند. نسخه و نوع/حدود سمت سرور نیز کنترل شوند؛ فقط اضافه‌کردن input کافی نیست.
- دادهٔ intake در اعلان عمومی، projection عمومی، نمونه یا گزارش نامجاز منتشر نشود. انتخاب «تحویل مرحله‌ای» تعهد/تسویه خودکار نیست. سطح محرمانگیِ انتخابی و سطح اعمال‌شده با ادعای امنیت ساختگی اشتباه نشوند؛ پذیرش اعمال سیاست فقط با تست مجوز واقعی.
