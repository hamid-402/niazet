# تست Load و Stress

این مرحله پنج مسیر پرریسک را با HTTP واقعی و PostgreSQL واقعی می‌سنجد: احراز هویت و Session، فهرست سفارش مشتری، صدور و مصرف Signed URL فایل، مشاهده و Verify هم‌زمان پرداخت، و اجرای هم‌زمان Worker.

## ایزولیشن و ایمنی

اسکریپت هر بار یک دیتابیس با پیشوند `niazat_load_` می‌سازد، migration و seed را روی همان دیتابیس اجرا می‌کند و API buildشده را روی پورت تصادفی محلی بالا می‌آورد. مقصد خارجی یا دیتابیس اصلی قابل تنظیم نیست. در بلوک `finally` پردازش API متوقف، اتصال‌ها terminate، دیتابیس موقت drop و فایل آپلودشده با کنترل مسیر پاک می‌شود. Driverهای پرداخت، اسکن فایل، پیامک و ایمیل فقط در حالت mock اجرا می‌شوند و Workerهای زمان‌بندی‌شده خاموش‌اند.

## پروفایل‌ها

- `npm run phase8:load-smoke`: مجموعاً ۲۱۸ درخواست محدود برای CI؛ تمام پاسخ‌های غیرمنتظره و 5xx ممنوع و برای هر سناریو بودجه p95 و حداقل throughput اعمال می‌شود.
- `npm run phase8:load-stress`: بیش از ۱۱۰۰ درخواست با concurrency بالاتر برای اجرای دستی روی ماشین pre-production هم‌اندازه production.

پیش‌نیاز هر دو دستور، build موفق API و دسترسی مدیریتی PostgreSQL از طریق `DATABASE_URL` است. CI پروفایل smoke را پس از migration و E2E اجرا و گزارش JSON را به مدت ۳۰ روز با نام `load-smoke-report` نگه‌داری می‌کند. اجرای stress باید روی runner اختصاصی و بدون هم‌زمانی با benchmark دیگری باشد؛ نتیجه وقتی قابل مقایسه است که CPU، RAM، نسخه PostgreSQL، تعداد replica و commit ثبت شوند.

## معیار پذیرش

گزارش برای هر سناریو تعداد درخواست، concurrency، RPS، p50، p95، p99، بیشینه latency و توزیع status code را ثبت می‌کند. علاوه بر بودجه latency/throughput، Verify هم‌زمان باید دقیقاً یک Payment موفق، یک Escrow و یک Invoice بسازد و اجرای هم‌زمان Worker باید دقیقاً یک `background_job_run` موفق داشته باشد. پاسخ 409 فقط در رقابت Idempotency پرداخت پذیرفته است و هیچ خطای شبکه، پاسخ ناشناخته یا 5xx قابل قبول نیست.
